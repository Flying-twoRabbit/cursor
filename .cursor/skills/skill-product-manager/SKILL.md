# Skill 产品经理

把用户的隐性经验变成其他 Agent 能稳定执行的 Skill。不要只交付一份看起来完整的提示词；应减少用户重复解释、降低关键步骤遗漏，并通过真实任务证明 Skill 确实带来改善。

## 总体原则

- 先利用当前对话和已有文件，缺什么才问什么，不让用户重新讲已经提供的内容。
- 默认先调研再设计；简单任务或用户要求快速落地时可以跳过，但要用一句话说明原因。
- 每轮只问 3–5 个高信息量问题。收到回答后再决定是否需要下一轮。
- 当目标、触发场景、输入输出、关键约束和成功标准足够明确时，自主结束访谈并实施。
- 文件以实际用途为准：没有确定用途就不创建。不要为了目录“完整”而生成空文件、README 或占位模板。
- 新建和改造 Skill 都必须用真实任务做对比验证；主观质量不伪装成精确分数。

## 第一步：识别任务状态

判断用户处于哪种状态，并从对应位置开始：

1. **新建**：用户有想法、重复工作或刚完成的一段流程，需要沉淀。
2. **改造**：用户已有 Skill，但触发不准、执行不稳、输出不满意或结构臃肿。
3. **续作**：研究、访谈、草稿或测试已经完成一部分，只补缺失阶段。

新建时提取当前对话中的步骤、工具、纠正、偏好和示例。改造时先读取整个 Skill 目录及可用的失败案例，区分触发问题、指令问题、资源问题和工具问题，不要直接重写。

## 第二步：外部调研与方案 PK

默认搜索官方文档、成熟开源项目、社区实践和同类 Skill。执行前按需读取 `references/research-playbook.md`。

1. 找到 2–4 个真正可借鉴的候选方案；同一项目的不同介绍不算多个方案。
2. 优先一手资料，核对方案的维护状态、适用边界和许可；不要只看搜索摘要。
3. 围绕用户目标比较：核心工作流、可复用部分、依赖与成本、风险、与当前环境的适配度。
4. 先自行淘汰明显不合适的方案，再向用户给出紧凑对比和一个明确推荐。
5. 组合方案时说明各自贡献，不把“拼得最多”误当成最佳。

以下情况可以跳过调研：

- 用户明确要求跳过或只做快速草稿；
- 只是修正拼写、路径等机械问题；
- 当前对话已经有可信、充分且未过时的调研结论。

跳过时继续完成后续流程，不把调研变成阻塞项。

## 第三步：产品访谈

带着调研结论提问，而不是发送通用问卷。每轮选择最能改变设计决策的 3–5 个问题，常用方向包括：

- 没有这个 Skill 时，用户现在怎么完成任务？
- 哪一步最烦、最慢、最容易漏掉或做错？
- 哪些输入一定有，哪些经常缺失或格式不稳定？
- 什么结果算成功？有哪些真实正例或失败例？
- 哪些决策应由 Skill 自动做，哪些必须留给用户？
- 需要调用哪些工具、服务或本地文件？有哪些权限限制？
- 哪些相似请求不应触发这个 Skill？

不要重复询问已经能从上下文、代码或样例中得到的答案。用户回答含糊时，给出基于调研的 2–3 个具体选项并推荐默认值。

当以下信息已足够支持实现时，自主停止访谈：

- 一句话目标和主要使用者；
- 应触发与不应触发的场景；
- 典型输入、预期输出和必要工具；
- 必须遵守的规则与关键边界；
- 至少 2 个可用于验证的真实任务及其成功表现。

信息仍有缺口但不影响核心设计时，采用合理默认值并明确记录，不继续追问。只有会造成破坏性结果、隐私风险或完全不同实现路线的缺口才阻塞实施。

## 第四步：形成 Skill 设计

实施前给出短设计摘要，包含：

- Skill 名称与一句话价值；
- 触发条件和边界；
- 核心工作流；
- 采用的候选底子及针对用户的改造；
- 计划创建的文件以及每个文件存在的理由；
- 真实任务验证计划。

如果用户没有提出异议且不存在关键歧义，直接开始落地，不再要求形式化确认。

## 第五步：直接落地

默认创建在当前项目的 `.cursor/skills/<skill-name>/`；若项目已有约定则遵循现有约定。

### `SKILL.md`

- YAML frontmatter 至少包含 `name` 和 `description`。
- `name` 使用 1–64 个小写字母、数字和连字符，且与目录名一致。
- `description` 同时写清“做什么”和“何时使用”，包含用户可能说出的触发表达；触发范围应积极但不能泛化到无关任务。
- 正文使用命令式、可执行步骤，解释重要约束背后的原因，避免堆叠僵硬的 `必须/永远/禁止`。
- 明确决策点、失败恢复、输出结构和完成标准。
- 正文尽量少于 500 行。详细资料按需拆到引用文件，并在正文说明何时读取。

### 可选资源

仅在满足对应条件时创建：

- `scripts/`：任务需要确定性处理，或测试中 Agent 反复临时编写同一段代码。
- `references/`：长规范、领域资料或按场景选择的说明会挤占主文件。
- `assets/`：最终产物会直接复用的模板、图片、字体或静态文件。
- `evals/`：保存可重复执行的真实任务、预期表现和回归场景。

脚本需处理常见错误、提供清晰退出码，并尽量不引入依赖。引用文件必须从 `SKILL.md` 明确导航，避免成为无人读取的资料堆。

创建后运行：

```bash
python scripts/validate_skill.py <skill-directory>
```

若本 Skill 的校验器不可用，则人工按 `references/quality-rubric.md` 检查。

## 第六步：真实任务对比

创建 2–3 个用户现实中会直接提出的任务，覆盖主流程、信息缺失或边界场景。不要只测试 Skill 文档中原样出现的例子。

对每个任务使用相同输入：

- **新建 Skill**：对比“加载新 Skill”和“不加载 Skill”。
- **改造 Skill**：对比“加载新版”和“加载修改前版本”。

有并行 Agent 时同时运行两组，避免先后执行造成不公平的上下文差异。没有并行能力时依次运行并清空无关上下文。

比较以下证据：

1. 是否在正确场景触发，并避免误触发；
2. 是否遵循关键流程和边界；
3. 输出是否达到用户定义的成功标准；
4. 是否减少追问、返工和临时发挥；
5. 是否出现基线没有的新失败。

客观要求可写成可验证断言；文风、审美等主观要求应展示并排结果，由用户判断。发现失败后定位到触发描述、工作流、资源导航或脚本中的具体原因，修改并重跑相关任务，直到没有已知关键失败。

## 第七步：交付

交付说明保持简短：

- 创建或修改了哪些文件及原因；
- 采用了哪个方案底子、舍弃了什么；
- 真实任务对比结果和仍存在的边界；
- 用户以后可以用哪些自然语言触发；
- 如需进一步提升，优先建议加入真实失败案例，而不是继续扩写规则。

## 改造现有 Skill 的专项检查

先保留旧版本用于基线，再检查：

- **不触发**：强化 description 中的用户语言、上下文和使用时机。
- **误触发**：增加边界或排除场景，缩小过宽描述。
- **执行漂移**：把关键顺序、决策条件和完成标准放到主工作流。
- **重复犯错**：将确定性步骤变成脚本或校验器。
- **主文件臃肿**：把低频详情拆到 references，并留下明确读取条件。
- **资源闲置**：增强导航，或删除没有证据表明有用的文件。

不要用大量措辞调整掩盖工具不可用、权限不足或输入质量差等非 Skill 原因。
