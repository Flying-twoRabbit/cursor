# Skill 方案调研手册

仅在需要外部调研时读取本文件。目标是找到可复用的设计底子，而不是堆链接。

## 来源优先级

1. 官方规范、官方示例和维护者文档
2. 有实际代码、版本记录和使用说明的开源项目
3. 由作者公开的生产实践或技术复盘
4. 社区教程、聚合列表和搜索摘要

低优先级来源适合发现线索，不适合作为关键结论的唯一依据。涉及当前版本、兼容性、许可和安全性时，回到一手资料核对。

## 候选筛选

每个候选至少应回答：

- 它解决的任务是否与用户目标相同，而不只是名字相似？
- 核心机制是什么？
- 有哪些可直接借鉴的工作流、脚本、模板或评测方法？
- 依赖哪些平台、服务、权限或运行环境？
- 是否仍在维护，是否有足够证据表明它真实可用？
- 许可和安全边界是否允许借鉴？

候选不足 2 个时，明确说明市场上没有足够成熟的同类方案，不要用低质量结果凑数。候选超过 4 个时，先内部淘汰，再展示最相关的 2–4 个。

## PK 维度

按任务选择真正影响决策的维度，通常包括：

| 维度 | 要回答的问题 |
|---|---|
| 目标匹配 | 能否直接解决用户最痛的步骤？ |
| 稳定性 | 是否有明确流程、错误处理和验证闭环？ |
| 改造成本 | 需要多少依赖、迁移或额外维护？ |
| 可移植性 | 是否绑定特定模型、平台或私有服务？ |
| 用户负担 | 是否减少重复说明和不必要确认？ |
| 可验证性 | 能否通过真实任务观察到改善？ |
| 风险 | 是否存在安全、隐私、许可或过时问题？ |

不要默认给所有维度打数字分。证据不足的精确分数会制造虚假确定性；简短的“强/中/弱 + 依据”通常更诚实。

## 推荐格式

```markdown
我找到并筛选了 N 个可借鉴方案：

| 方案 | 可借鉴点 | 主要不足 | 适配度 |
|---|---|---|---|
| A | ... | ... | 强 |
| B | ... | ... | 中 |

推荐以 A 为底子，并吸收 B 的某项机制。
原因：它最直接解决 [用户痛点]，同时避免 [主要代价]。
```

推荐必须明确，不把最终筛选工作重新丢给用户。只有两种路线会导致本质不同且无法从现有信息判断时，才让用户选择。

## 将调研带入访谈

调研完成后，把通用问题改成带上下文的问题：

- 不问：“你想怎么测试？”
- 改问：“方案 A 用有/无 Skill 的任务对比，方案 B 只做格式校验。你的流程包含主观判断，我建议保留两组真实输出并排检查；是否还需要机器可判定的规则？”

- 不问：“需要脚本吗？”
- 改问：“你提到每次都要整理同一种 CSV。这个步骤适合做成确定性脚本；列名是否固定，还是要支持别名？”

这样让用户提供领域判断，而不是替 Skill 产品经理完成方案设计。
