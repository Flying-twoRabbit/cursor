# Skill 质量检查表

在创建、改造和最终交付前使用。检查失败时修正具体原因，不要为了“通过”而删除必要能力。

## 1. 定位与触发

- [ ] 目录名与 frontmatter 的 `name` 一致
- [ ] `name` 只含小写字母、数字和连字符，长度不超过 64
- [ ] `description` 同时说明做什么、何时使用
- [ ] `description` 包含用户会自然说出的触发场景
- [ ] 与邻近 Skill 的职责边界清楚，不会大范围误触发

## 2. 工作流

- [ ] 主路径是可执行步骤，不是背景知识堆积
- [ ] 已利用上下文，避免重复向用户索取已知信息
- [ ] 关键决策有明确条件
- [ ] 输入不足、工具失败或结果不确定时有恢复办法
- [ ] 完成标准和输出形式足够清楚
- [ ] 重要约束说明了原因，规则没有互相冲突

## 3. 信息结构

- [ ] `SKILL.md` 保留高频、关键内容，尽量少于 500 行
- [ ] 每个 reference 都有明确读取时机和正文入口
- [ ] 每个 script 都对应重复或确定性任务
- [ ] 每个 asset 都会直接用于最终产物
- [ ] 没有空目录、占位文档或重复说明
- [ ] 路径统一使用 `/`

## 4. 脚本

- [ ] 不依赖未声明的包或系统工具
- [ ] 参数和错误信息对 Agent 可操作
- [ ] 常见错误返回非零退出码
- [ ] 不静默覆盖用户数据
- [ ] 已执行成功路径和至少一个失败路径

## 5. 真实任务评测

- [ ] 至少 2 个真实任务，覆盖主流程和一个边界或信息缺失场景
- [ ] 新建 Skill 与无 Skill 基线比较；改造 Skill 与旧版比较
- [ ] 两组使用完全相同的任务和输入
- [ ] 断言来自用户成功标准，而不是照抄 Skill 措辞
- [ ] 主观结果采用并排审阅，没有伪造精确评分
- [ ] 关键失败已经修复并重跑
- [ ] 没有只为测试样例写死的规则

## 6. 精简复核

逐个文件询问：

1. 删除它会让哪个真实任务变差？
2. 它为什么不能更短，或合并到更合适的位置？
3. Agent 如何知道何时读取或执行它？

三问都答不出来的文件应删除。内容只是“可能以后有用”时，等真实案例出现再添加。
